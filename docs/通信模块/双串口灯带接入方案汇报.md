# 双串口灯带接入方案汇报

## 背景

当前项目是 Android 上位机，原有通信链路通过 232 串口连接电机控制板：

- 电机串口路径：`/dev/ttyS9`
- 原有服务文件：`utils/serialService.js`
- 原有配置文件：`utils/serialConfig.js`

本次新增一个 485 串口灯带控制器：

- 灯带串口路径：`/dev/ttyS4`
- 串口参数：`115200` 波特率，`8` 位数据位，`1` 位停止位，无奇偶校验
- 通信协议：CM-XS 串口协议
- 通信模式：响应式一问一答
- 当前目标：提供手动灯带控制页面，分别测试连接、开启、关闭、开启 5 秒后关闭

## 什么是双串口方案

这里的“双串口方案”不是在一个串口上挂两个设备，也不是通过修改同一个串口路径来切换设备。

本项目中的双串口方案指的是：

- App 同时打开两个不同的 Linux 串口设备节点。
- 电机继续使用 `/dev/ttyS9`。
- 灯带独立使用 `/dev/ttyS4`。
- 两个串口分别拥有自己的 `portId`。
- 两个设备的连接、发送、读取、关闭互不复用运行时状态。

也就是说，电机和灯带在软件层面是两个独立的通信通道：

```txt
App
├─ serialService.js       -> /dev/ttyS9 -> 232 -> 电机控制板
└─ lightStripService.js   -> /dev/ttyS4 -> 485 -> 灯带控制器
```

底层 UTS 串口插件本身已经支持多个串口实例。插件内部使用串口句柄 `portId` 管理不同串口，因此只要上层服务不要把多个设备混在同一个单例状态里，就可以同时管理多个串口。

### portId 是什么

`portId` 是底层 UTS 串口插件在 `openSerial()` 成功后返回的串口句柄 ID。

它不是物理串口路径，也不是设备地址。它的作用是让后续 `writeSerial()`、`readSerial()`、`closeSerial()` 知道要操作哪一个已经打开的串口实例。

例如：

```txt
openSerial('/dev/ttyS9') -> 返回 portId=1
openSerial('/dev/ttyS4') -> 返回 portId=2

writeSerial({ portId: 1, ... }) -> 写入电机串口
writeSerial({ portId: 2, ... }) -> 写入灯带串口
```

`portId` 工作在 App 的 UTS 串口插件层和 JS 服务层之间：

```txt
JS 服务层
├─ serialService.js 保存电机 runtime.portId
└─ lightStripService.js 保存灯带 runtime.portId

UTS 插件层
└─ 根据 portId 从内部串口实例池中找到具体 SerialPort 对象

Android/Linux 设备层
├─ /dev/ttyS9
└─ /dev/ttyS4
```

所以，`portId` 是“已经打开的串口实例”的软件句柄，用来区分多个同时存在的串口连接。

### 电机通信以前有没有 portId

电机通信以前就已经有 `portId`，不是本次从“没有 portId”改成“有 portId”。

原来的电机流程是：

```txt
serialService.connect()
-> openSerial('/dev/ttyS9')
-> 插件返回 portId
-> serialService 保存到 runtime.portId
-> 后续 readSerial/writeSerial/closeSerial 都使用这个 runtime.portId
```

本次变化不是给电机新增 `portId` 机制，而是把“只有电机一个服务保存一个 `portId`”扩展为“电机服务和灯带服务分别保存自己的 `portId`”。

变化前：

```txt
serialService.runtime.portId -> /dev/ttyS9
```

变化后：

```txt
serialService.runtime.portId      -> /dev/ttyS9
lightStripService.runtime.portId  -> /dev/ttyS4
```

因此，电机原有通信流程没有被改成新的模式，它仍然按原来的 `portId` 方式工作。新增的是灯带服务也独立打开串口，并独立持有自己的 `portId`。

## 为什么不能直接复用 serialService.js

`utils/serialService.js` 是为电机控制板设计的单例服务，它内部只有一份运行时状态：

- 一个 `runtime.portId`
- 一个 `runtime.rxBuffer`
- 一个读轮询状态
- 一个发送队列
- 一套事件监听器
- 一套电机工作状态机

同时它还强绑定了电机协议：

- A9 上行帧解析
- D180 下行帧构建
- 5Hz 工作状态周期发送
- 停力序列
- 电机力控模式枚举

如果把灯带直接塞进 `serialService.js`，会产生几个问题：

- 已连接电机后，再连接灯带时会复用已有 `portId`，无法真正打开第二个串口。
- 电机的常驻读轮询可能会干扰灯带一问一答的响应读取。
- 灯带协议和电机协议混在一起，后续维护成本高。
- 电机安全逻辑，例如停力序列，不应该和灯带控制逻辑耦合。

因此，本次没有改造 `serialService.js` 的核心状态机，而是新增独立的灯带服务。

## 本次实现方式

### 1. 扩展串口配置

在 `utils/serialConfig.js` 中新增了多设备配置：

```js
export const SERIAL_DEVICES = {
	motor: {
		path: '/dev/ttyS9',
		baudRate: 115200,
		dataBits: 8,
		stopBits: 1,
		parity: 'none'
	},
	lightStrip: {
		path: '/dev/ttyS4',
		baudRate: 115200,
		dataBits: 8,
		stopBits: 1,
		parity: 'none'
	}
}
```

原有的 `SERIAL_DEVICE_PATH` 和 `SERIAL_BAUD_RATE` 保留，保证电机旧代码不受影响。

### 2. 新增灯带独立服务

新增文件：

```txt
utils/lightStripService.js
```

该服务只负责灯带通信，内部维护自己的运行时状态：

- `portId`
- `connectPromise`

当前阶段只做最小验证，所以没有引入状态机、事件系统、请求队列和复杂解析逻辑。服务只负责三件事：

- 打开 `/dev/ttyS4` 并保存灯带自己的 `portId`。
- 按 CM-XS 协议拼出开灯、关灯 HEX 帧。
- 写出命令后短暂尝试读取应答，读不到只记录日志，不阻断页面操作。

### 3. 按 CM-XS 协议构建灯带帧

灯带协议帧格式：

```txt
帧头      地址  指令  数据长度  有效数据  帧尾
5E5F      00    00    0002      000A      5AFE
```

当前实现的开启命令：

```txt
发送：5E5F00000002000A5AFE
应答：5E5F00100002000A5AFE
```

当前实现的关闭命令：

```txt
发送：5E5F00000002FFFF5AFE
应答：5E5F00100002FFFF5AFE
```

当前最小版本只打印应答，不做严格应答校验。

这样处理是因为现阶段优先验证两件事：

- `/dev/ttyS4` 能否独立打开。
- 灯带能否收到命令并产生物理动作。

如果后续确认控制器稳定返回应答，再补充严格校验也不迟。

### 4. 不做常驻轮询

灯带是响应式协议，一问一答。

因此灯带服务没有采用电机那种常驻轮询读取模式，而是采用：

```txt
发送命令 -> 短暂尝试读取应答 -> 在页面接收区记录结果
```

这样做的原因是：

- 灯带没有持续上报数据的需求。
- 当前只验证开关灯动作，不需要长期占用读循环。
- 读不到应答时仍要允许继续手动测试，便于判断是“写不通”还是“只是不回包”。
- 后续如果灯带要参与正式业务联动，再根据实际回包情况补充严格的一问一答封装。

### 5. 在首页接入手动控制页面

首页新增 `灯带控制` 按钮，跳转到：

```txt
pages/serial-test/light-strip-control
```

页面提供：

```txt
连接灯带串口
开启灯带
关闭灯带
开启 5 秒后关闭
接收区查看应答或无应答提示
```

这样可以手动拆开每一步测试，比启动自动演示更适合排查硬件链路。

## 为什么这样设计

### 1. 保持电机通信稳定

电机通信已经包含工作态发送、读取、停力等安全相关逻辑，不适合在同一个服务里混入灯带协议。

把灯带拆成独立服务后，灯带调试失败不会影响电机的连接状态和工作状态。

### 2. 符合两个设备的协议差异

电机是持续通信模型：

```txt
周期发送 D180 -> 持续读取 A9
```

灯带是响应式模型：

```txt
发送一条命令 -> 等待一条应答
```

两者通信模型不同，所以应该使用不同的服务实现。

### 3. 便于后续扩展

后续如果需要增加灯带功能，例如：

- 指定启动效果
- 内置花样调整
- 亮度控制
- 训练状态联动灯效

可以继续在 `lightStripService.js` 中增加方法，不需要动电机服务。

### 4. 更容易定位问题

双串口拆分后，日志也更清晰：

```txt
[serialService] ...
[lightStripService] ...
```

如果灯带无响应，可以直接关注 `[lightStripService]` 日志，不需要从电机通信日志中混合排查。

## 当前验证目标

真机运行后，在灯带控制页面手动点击按钮，HBuilderX 日志中应看到：

```txt
[lightStripService] 正在连接灯带串口...
[lightStripService] 灯带串口连接成功, portId: ...
[lightStripService] turnOn send: 5E5F00000002000A5AFE
[lightStripService] response: 5E5F00100002000A5AFE
[lightStripService] turnOff send: 5E5F00000002FFFF5AFE
[lightStripService] response: 5E5F00100002FFFF5AFE
```

如果控制器不返回应答，日志中可能出现：

```txt
[lightStripService] 读取灯带应答失败，继续执行: ...
```

这不代表串口一定失败，需要结合灯带是否产生物理动作判断。

硬件现象应为：

```txt
点击开启后灯带开启
点击关闭后灯带关闭
点击“开启 5 秒后关闭”后，灯带开启并在 5 秒后关闭
```

## 后续建议

当前 `pages/serial-test/light-strip-control.vue` 是临时手动测试入口。

真机验证通过后，建议：

- 根据训练流程，把灯带控制接入明确的业务节点，例如训练开始、训练结束、异常状态。
- 如果后续灯带协议命令增多，再补充 `requestCommand` 或命令枚举，避免散落硬编码 HEX。
