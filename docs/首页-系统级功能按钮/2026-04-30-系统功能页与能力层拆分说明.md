# 系统功能页与能力层拆分说明

## 背景

首页右上角的 `control-panel` 包含一组系统功能按钮，例如：

- `wifi`
- `bluetooth`
- `voice`
- `light`
- `setting`

这类按钮的共同点是：

- 页面长得像系统设置页，但 UI 其实是业务页面自己实现的
- 页面里的数据和动作依赖系统级能力，例如 WiFi 扫描、蓝牙扫描、摄像头调用
- 如果把权限申请、平台判断、系统 API 调用都直接写进页面，后续维护会迅速变乱

因此，这次对 WiFi 功能做了结构调整，把“页面展示”和“系统能力”拆开。

## 本次调整目标

目标不是只把 WiFi 做出来，而是先建立一套后续可复用的系统功能架构。

拆分后要满足：

- 页面只负责展示和交互
- 权限申请有统一入口
- 不同系统能力按模块单独管理
- `manifest.json` 只负责静态权限声明
- 后续新增蓝牙、摄像头等功能时，可以沿用同样结构

## 当前文件结构

当前与系统功能相关的结构如下：

```text
pages/
  index/
    index.vue
  system/
    wifi.vue

utils/
  system/
    permission-service.js
    wifi/
      wifi-service.js

manifest.json
```

对应职责如下：

- `pages/index/index.vue`
  - 首页系统按钮入口
  - 例如点击 `wifi` 后跳转到 `pages/system/wifi`

- `pages/system/wifi.vue`
  - WiFi 页面 UI
  - 展示当前网络
  - 展示附近网络列表
  - 处理用户点击、输入密码、触发连接
  - 不直接处理底层权限和平台能力细节

- `utils/system/permission-service.js`
  - 统一处理 Android 权限申请
  - 目前先抽出 WiFi 所需定位权限
  - 后续蓝牙、摄像头权限也应继续放在这里统一管理

- `utils/system/wifi/wifi-service.js`
  - 统一处理 WiFi 能力
  - 包括初始化、扫描、连接、事件监听、销毁、错误消息转换

- `manifest.json`
  - 负责 Android 静态权限声明
  - 例如 `ACCESS_WIFI_STATE`、`CHANGE_WIFI_STATE`、定位权限等

## 为什么不能把系统逻辑直接写在页面里

如果把 `plus.android.requestPermissions`、`uni.startWifi`、`uni.getWifiList`、`uni.connectWifi` 都写在 `wifi.vue` 里，会有几个问题：

- 页面职责过重，UI 改动和系统能力改动混在一起
- 后续做蓝牙页时，会复制大量类似代码
- 平台兼容逻辑会分散在多个页面
- 错误处理口径不一致
- 页面变得难读、难测、难复用

页面应该是“使用能力”，不应该是“定义能力”。

## 这次 WiFi 是怎么拆的

### 1. 静态权限声明放在 `manifest.json`

WiFi 功能相关的 Android 权限声明放在：

- `ACCESS_WIFI_STATE`
- `CHANGE_WIFI_STATE`
- `ACCESS_NETWORK_STATE`
- `ACCESS_FINE_LOCATION`
- `ACCESS_COARSE_LOCATION`

这里属于打包配置，不应写在页面或 service 里。

### 2. 动态权限申请放在 `permission-service.js`

`requestWifiPermissions()` 负责：

- 在 `APP-PLUS` 环境下调用 `plus.android.requestPermissions`
- 统一处理允许/拒绝结果
- 返回 Promise，供具体能力模块调用

这层的意义是：

- 页面不直接接触原生权限 API
- WiFi、蓝牙、摄像头都能复用同一套权限组织方式

### 3. WiFi 能力放在 `wifi-service.js`

`wifi-service.js` 当前负责：

- `ensureWifiSupport`
  - 判断当前构建是否启用 `uni-WiFi`
  - 判断是否为可用环境

- `initWifiService`
  - 申请权限
  - 初始化 `startWifi`
  - 绑定列表监听和连接监听

- `getConnectedWifi`
  - 获取当前连接 WiFi

- `scanWifiList`
  - 扫描附近 WiFi

- `connectWifiNetwork`
  - 发起连接
  - 内部处理 Android 版本差异

- `stopWifiService`
  - 页面销毁时清理监听和 WiFi 模块

- `getWifiErrorMessage`
  - 把错误码转换成可读中文提示

### 4. 页面只保留交互层

`pages/system/wifi.vue` 现在主要只做：

- 接收 WiFi 列表并渲染
- 显示当前连接名称
- 点击某一项展开密码框
- 调用 service 发起扫描和连接
- 页面卸载时调用 service 清理

这就是推荐的页面职责边界。

## 页面层和能力层的关系

可以把这套结构理解成三层：

### 第一层：页面层

位置：

- `pages/system/*.vue`

职责：

- 负责 UI 展示
- 负责按钮点击、表单输入、状态显示
- 不直接触碰原生权限和系统 API 细节

### 第二层：能力层

位置：

- `utils/system/wifi/wifi-service.js`
- 后续可扩展到 `bluetooth/bluetooth-service.js`
- 后续可扩展到 `camera/camera-service.js`

职责：

- 封装系统 API
- 做平台判断
- 做版本兼容
- 做监听绑定和释放
- 统一错误处理

### 第三层：权限与打包配置层

位置：

- `utils/system/permission-service.js`
- `manifest.json`

职责：

- 统一申请动态权限
- 统一声明静态权限

## 后续建议的扩展目录

如果继续做蓝牙、摄像头，建议沿用当前模式：

```text
utils/
  system/
    permission-service.js
    wifi/
      wifi-service.js
    bluetooth/
      bluetooth-service.js
    camera/
      camera-service.js
```

对应页面可以继续放在：

```text
pages/
  system/
    wifi.vue
    bluetooth.vue
    camera.vue
```

这样能保持：

- 页面目录按功能入口组织
- 系统能力目录按能力类型组织

## 为什么 `wifi-service.js` 要放到 `wifi/` 文件夹下

这是为了给后续扩展留空间，而不是只放一个孤立文件。

后续 WiFi 模块可能还会新增：

- `wifi-constants.js`
- `wifi-mapper.js`
- `wifi-permission-note.md`
- `wifi-device-adapter.js`

如果一开始就放进 `utils/system/wifi/`，后续扩展不会再触发目录迁移。

## 目前已知的平台边界

当前 WiFi 页面是基于 uni-app 官方 WiFi API 接入的，注意以下限制：

- H5 预览不能当作真实 WiFi 调试环境
- 应优先在 Android App 真机中验证
- Android 10 及以上连接 WiFi 时通常会进入系统连接流程，不能简单理解为完全静默直连
- 即使代码无误，也可能因为系统设置、权限状态、ROM 限制导致扫描或连接表现不同

这意味着：

- 页面 UI 可以在 H5 看
- 真正的系统能力必须在 Android 真机看

## 维护建议

### 1. 不要把新的系统 API 再写回页面

例如以后做蓝牙时，不建议在 `pages/system/bluetooth.vue` 里直接写：

- `plus.android.requestPermissions`
- `uni.openBluetoothAdapter`
- `uni.startBluetoothDevicesDiscovery`

应该先抽到 `utils/system/bluetooth/bluetooth-service.js`。

### 2. 权限名称和错误文案尽量集中管理

这样做的好处是：

- 页面提示口径统一
- 后期排查问题更快
- 改权限策略时不会全项目散改

### 3. 页面销毁时要清理监听

系统能力模块普遍带监听器，例如：

- WiFi 列表变化
- WiFi 连接状态变化
- 蓝牙发现设备
- 摄像头状态变化

如果不清理，后续很容易出现：

- 重复回调
- 内存占用增加
- 页面切换后状态错乱

### 4. 先抽象“结构”，再抽象“通用”

目前只需要先保证：

- 权限层独立
- WiFi 能力层独立

不要一开始就为了“通用”写过大的超级 service。先按能力拆模块，后面有真实复用时再继续合并共性。

## 本次改动的核心结论

这次不是简单“新增一个 WiFi 页面”，而是确定了一条后续系统能力开发原则：

- 系统按钮页面是页面层
- 原生权限和系统 API 是能力层
- 静态权限属于配置层
- 三层分开，后续蓝牙、摄像头、系统设置页都按同样方式扩展

这套结构的目标是让项目在系统功能继续增多时，仍然保持可读、可改、可维护。
